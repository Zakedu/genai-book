# 바이브 코딩 (Vibe Coding)

## 개요

**바이브 코딩(Vibe Coding)**은 개발자가 코드를 직접 한 줄씩 작성하는 대신, **자연어로 의도(‘바이브’)를 전달하고 AI가 코드를 생성**하도록 하는 개발 방식입니다. 2025년 초 이 용어가 널리 쓰이기 시작한 뒤, 2026년에는 "생성 후 반드시 검증한다"는 실무 관행이 더해지며 하나의 개발 흐름으로 자리 잡았습니다.

!!! abstract "학습 목표"
    - 바이브 코딩과 전통적 코딩의 차이를 설명할 수 있다
    - 바이브 코딩이 왜 '검증 단계'와 한 쌍으로 다뤄지는지 이해한다
    - 어떤 작업에 적합하고 어떤 작업에 부적합한지 판단할 수 있다

## 전통적 코딩과의 차이

| 구분 | 전통적 코딩 | 바이브 코딩 |
|------|------------|------------|
| 입력 | 프로그래밍 언어 | 자연어 의도 |
| 개발자 역할 | 코드 작성자 | **의도 설계자 · 검증자** |
| 속도 | 느림 | 빠름(프로토타이핑에 특히) |
| 위험 | 버그는 작성 중 인지 | 생성 코드를 **읽지 않으면 위험** |

핵심 전환은 개발자의 역할이 **"타이핑하는 사람"에서 "무엇을·왜 만들지 정하고 결과를 검증하는 사람"**으로 옮겨간다는 점입니다.

## 왜 '검증'이 반드시 따라오는가

바이브 코딩의 가장 큰 함정은 **"돌아가니까 맞겠지"**입니다. AI가 만든 코드는 그럴듯해 보여도 보안 취약점, 엣지 케이스 누락, 잘못된 라이브러리 사용을 포함할 수 있습니다. 그래서 2026년의 성숙한 바이브 코딩은 항상 다음을 동반합니다.

1. **생성 코드 읽기** — 이해하지 못한 코드는 병합하지 않는다
2. **테스트** — AI에게 테스트도 함께 생성시키되, 테스트 자체도 검토
3. **보안 검토** — [프롬프트 인젝션](../../security/prompt-injection.md)·비밀키 노출·의존성 취약점 확인
4. **소규모 반복** — 한 번에 큰 덩어리보다 작은 단위로 생성·검증

!!! warning "책임은 개발자에게"
    AI가 코드를 썼더라도, 배포된 코드의 버그·보안 사고 책임은 사람에게 있습니다. 바이브 코딩은 '검증 면제'가 아니라 '검증 대상의 이동'입니다.

## 적합 vs 부적합

!!! success "적합한 경우"
    - 프로토타입·MVP·일회성 스크립트
    - 익숙하지 않은 라이브러리의 예제 코드 초안
    - 반복적인 보일러플레이트

!!! failure "신중해야 할 경우"
    - 보안·결제·개인정보를 다루는 핵심 로직
    - 대규모 프로덕션 코드베이스에 대한 광범위한 자동 수정
    - 개발자가 결과를 검증할 역량이 없는 도메인

## 시험 대비 핵심 정리

- 바이브 코딩 = **자연어 의도 → AI 코드 생성**, 개발자는 **의도 설계자·검증자**로 전환
- "돌아가니까 맞겠지"가 최대 함정 → **읽기·테스트·보안검토**가 필수 동반
- 책임은 사람에게 — '검증 면제'가 아니라 '검증 대상의 이동'
- 프로토타입엔 강력, 보안·핵심 로직엔 신중
